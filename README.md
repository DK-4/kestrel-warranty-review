# Kestrel Home — Warranty Claim Fraud Ranking

A fraud-risk ranking system for Kestrel Home's warranty claims: given ~800
claims/month and an investigation desk that can only review ~40, the model
ranks claims by fraud probability so the highest-risk ones go to human
investigators first. See `data/data-pack-README.txt` and
`data/email-thread.txt` for the original brief.

## Status

**Done:** data cleaning, point-in-time feature engineering, exhaustive
leakage test, temporal validation harness, and an honest comparison of
four models (do-nothing baseline, logistic regression, HistGradientBoosting,
and its class-weighted variant).

**Key validation result** (3-month held-out window, Apr-Jun 2026, mirroring
the actual train->test transition — see `reports/validation_report.json`
for full numbers, regenerate anytime with `python src/evaluate.py`):

- All three real models beat the baseline on ranking quality (PR-AUC
  ~0.10-0.11 vs. a ~0.021 random-prevalence rate — a genuine ~5x lift,
  modest but real for a hard, rare-event problem with only 141 fraud
  examples total).
- Chosen model: **HistGradientBoostingClassifier** (unweighted). Its
  class-weighted variant performs about the same on ranking (checked
  directly — neither shows the probability-compression problem that can
  come with reweighting), so the simpler, unweighted default was kept.
- **Important finding, not assumed going in:** always using the full
  40-claims/month investigation capacity is NOT the profit-maximizing
  policy at the current claim-value profile. Net rupee value (fraud
  value caught, minus investigation cost, minus goodwill cost on
  legitimate claims held) peaks at **~7 claims/month** (₹14,875 net over
  the 3-month validation window) and goes negative past ~17/month —
  see the k-sweep in `reports/validation_report.json`. A confidence
  threshold that sends fewer, higher-scored claims to investigation
  outperforms always filling every slot. (An earlier draft of this
  README mislabeled this as "~20/month" due to a units bug in the sweep
  script — k was total-over-3-months, not per-month. Fixed; see
  `src/evaluate.py`.)

**Known, disclosed model limitation:** the model under-weights partner
history specifically for small claims (<Rs 2,000). That segment actually
has a *higher* fraud rate than the rest of the book (3.2% vs 1.05%), and
partner history still correlates with fraud within it (r~0.24) — but
claim size dominates the model's early splits, so a known bad partner's
small claims currently score lower than their real risk would suggest. A
monotonic constraint was tested as a fix; it didn't improve validated
PR-AUC or rupee value, so it wasn't shipped. See `memo.md` section 5.

**Not yet built:** submission-form.md — no template for this was ever
provided in the task materials, so rather than invent questions we
haven't been asked, this is left for you to supply if one exists.

## predictions.csv

Generated by `python src/predict.py`, which retrains the champion model
(HistGradientBoostingClassifier) on the **full** 15-month decided
training set and scores the real test set. Validated row-for-row
against `data/sample_submission.csv` (same claim_ids, same order) —
assertions in the script fail loudly if that ever breaks.

**Operating point note:** the validated k-sweep (see above) found net
value peaks around 7 claims/month, not the full 40/month capacity.
`src/predict.py` reads this recommended k directly from
`reports/validation_report.json` (never hardcoded — HGB results aren't
bit-identical across scikit-learn versions, see below) and reports the
cutoff for each test month. `reports/flagged_claims_with_reasons.csv`
has the resulting ~21 claims (7 x 3 months) that would be flagged, each
with up to 3 rule-based reasons grounded in real feature values (no LLM).

## Reproducibility note

`requirements.txt` pins exact versions (not `>=`) because
`HistGradientBoostingClassifier` is not guaranteed bit-identical across
scikit-learn versions even with a fixed `random_state` — confirmed in
practice: the same code on scikit-learn 1.9.1 vs 1.8.0 produced a
different champion-model fit and a different k-sweep peak. Use the
pinned versions to reproduce the exact numbers in this README and in
`memo.md`.

## Running the API and UI

```bash
python src/predict.py                                    # must run first -- creates models/model.joblib
uvicorn src.api:app --reload --app-dir .                  # POST /predict, GET /health
streamlit run src/streamlit_app.py                        # one-page claim lookup tool
```

Both share the exact same scoring logic (`src/inference.py`) as
`predictions.csv` — verified directly: scoring the same claim through
`ClaimScorer` and through the batch pipeline gives identical scores.

**Testing disclosure:** this sandbox has no network access, so `fastapi`,

syntax/import correctness of both files. Please confirm `uvicorn` and


## Run it

```bash
# Clean the data and print a summary
python src/data.py

# Build point-in-time features and print a summary
python src/features.py

# Run the leakage test suite (exhaustive: every row, every partner)
pytest -v
# or
python tests/test_no_leakage.py

# Run temporal validation + model comparison, regenerate reports/validation_report.json
python src/evaluate.py

# Retrain champion on full history, generate predictions.csv + explanations
python src/predict.py
```

All of the above should run with no setup beyond `pip install -r
requirements.txt` and a populated `data/` folder.

## Why point-in-time features matter here

The single highest-risk bug in this kind of project is a feature like
"partner's historical fraud rate" computed using each partner's *entire*
claim history — including claims that happened after the one being
scored. That leaks the future into the past: it inflates validation
metrics beautifully and then falls apart on genuinely new data.
`src/features.py` builds this as a strictly expanding window (a claim
only ever sees *earlier* claims from the same partner), and
`tests/test_no_leakage.py` proves it — for every one of the 11,146
training rows, not a sample — by independently recomputing the "ground
truth" prior count with a slow, obviously-correct method and asserting
it matches. The test suite also includes a negative control: it was
run against a deliberately buggy whole-history version of the same
feature during development, and correctly failed on every affected row.
